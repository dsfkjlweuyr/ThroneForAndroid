## Context

参见 `proposal.md` 的问题动机。真机诊断已经区分出两个连续但独立的故障：

1. `buildChain` 在处理共享节点时先把前一跳 detour 写成预计算标签，之后才查询 `globalOutbounds` 并跳过已生成节点。若共享节点先作为另一个额外出站生成，链留下一个不存在的标签。
2. sing-box 的 `Start` 在依赖检查失败时会回滚内部资源，但当前 Go 包装状态仍为 started。Android 随后的失败清理调用 `Close`，底层返回 `file already closed`，该错误越过服务错误边界触发默认崩溃处理器。

当前约束是保持目标官方 sing-box 版本不变，不在本地进行 Android/Go 编译；实现必须分批交由 CI 与真机反馈。已有诊断日志应在两个批次验证完成前保留，以便关联 Android proxy ID、Go box ID 和状态转换。

## Goals / Non-Goals

**Goals:**

- 让链成员复用与构建顺序无关，所有生成引用都指向最终存在的标签。
- 用自动化测试固定“普通主节点 + 共享节点 + 包含共享节点的链”拓扑。
- 让启动部分失败后的关闭和重复关闭安全、可诊断且不导致 Android 后台进程崩溃。
- 保留原始启动错误作为服务失败原因，不用后续清理错误覆盖它。

**Non-Goals:**

- 不重写整个链解析算法、数据库模型或路由规则模型。
- 不改变正常启动、正常关闭、节点显示名称或流量统计映射。
- 不升级 sing-box，不吞掉任意未知关闭错误，也不把所有关闭错误一概视为成功。
- 不在本变更中移除生命周期诊断日志；日志精简可在稳定验证后另行处理。

## Decisions

### 1. 在建立链边之前解析共享节点的最终标签

对每个链成员，先查询该成员是否已经存在于全局出站映射；若已存在，当前链边直接引用映射中的最终标签，并跳过重复对象构建。只有尚未生成的成员才计算并注册新标签，然后参与 outbound/endpoint 构建。

这保证 detour 使用的标签与全局复用决策来自同一个事实来源，避免“先写边、后发现节点复用”的时序错误。无论共享节点是可读名称、`g-<id>` 还是 endpoint 标签，链都只使用已确定的最终值。

备选方案是发现复用后回头改写上一跳 detour。该方案依赖已构建对象的可变状态，对外部插件路由规则、endpoint 和未来更多边类型容易漏改，因此不采用。

### 2. 增加最终拓扑不变量检查作为测试辅助，而非运行时替代修复

测试应从最终 JSON 收集 endpoint/outbound 标签，并验证 detour、selector 成员及 route final 全部可解析。核心回归场景必须控制构建顺序：共享节点先独立生成，包含它的链后生成。

运行时可以保留当前脱敏 `ChainTopologyTrace` 作为证据，但不得仅靠检测到 unresolved 后临时删除出站或改走 direct；静默降级会改变用户路由语义。

### 3. 在 libcore 中明确失败关闭状态，并让关闭成为幂等操作

Go 包装层应将状态机从模糊的整数语义整理为至少可区分：new、starting/started、start-failed-or-closing、closed。`Close` 必须在锁内只执行一次底层释放，并在返回前稳定进入 closed。

当 `Start` 返回错误时，包装层记录原始错误和失败状态。后续 `Close` 若收到可判定为底层启动回滚已完成的“资源已关闭”结果，应将其作为清理完成处理并记录诊断，而不是返回给 JNI 调用方覆盖原始错误。未知错误仍返回，由 Android 的受控清理边界记录。

备选方案只在 Kotlin 中对字符串 `file already closed` 做 `runCatching`。该方案依赖错误文案、无法保护其他 JNI 调用方，也没有修复 Go 对实例状态的错误表达，因此只可作为 Android 最后防线，不作为唯一修复。

### 4. Android 服务清理保留受控错误边界

Android 侧应确保失败清理不会从主线程协程逃逸到默认未捕获异常处理器。原始 `Start` 错误用于 `service_failed` 状态；清理错误单独记录。若 Go 层已正确归一化幂等关闭，Android 路径正常完成；若出现未知关闭错误，服务仍应完成必要的引用清除和状态转换，同时将错误作为诊断而非替代原始启动错误。

此边界不是吞错：必须记录异常类型、实例身份和生命周期阶段。正常运行中的显式停止若遇到未知资源错误，仍需要可观测，但不能让清理协程破坏进程。

### 5. 两批滚动交付

批次 1 仅修复配置拓扑和 JVM 回归测试。通过 CI 与真机验证后，批次 2 才调整 Go/Android 关闭生命周期及其测试。这样可以分别证明首发错误消失，以及即使人为制造启动失败也不会再崩溃。

## Risks / Trade-offs

- [共享标签提前解析可能影响流量映射或可读名称] → 回归验证 `profileTagMap`、`trafficMap` 与主链/额外链两种构建顺序，要求仅引用目标变化，不改变节点归属。
- [底层“已关闭”错误缺少稳定类型] → 优先使用 Go 标准错误判定或受控状态事实；若目标版本只返回文本，封装最窄的兼容判定并用测试固定，禁止宽泛忽略所有错误。
- [Android 与 Go 双层容错掩盖未知问题] → Go 只归一化已知幂等关闭，Android 对其他错误保留结构化日志和实例 ID，但确保服务状态收敛。
- [诊断日志在 debug 配置中包含过多生成配置] → 本变更新增/保留的生命周期与拓扑日志仅记录标签、ID、状态和错误，不新增认证材料；现有完整 debug 配置输出不在本变更范围。
- [两个批次相互依赖导致验证混淆] → 批次 1 必须先证明原复现拓扑能够启动；批次 2 使用人为无效依赖或专用测试夹具验证失败清理，而不依赖批次 1 的旧缺陷继续存在。

## Migration Plan

1. 发布批次 1 到 CI，执行 Android JVM 配置测试；真机导入原复现数据，选择普通节点 2913 并保留同时引用 3045/3046 的规则，确认配置无 unresolved 且服务成功启动。
2. 收到批次 1 成功证据后发布批次 2，执行 Go 生命周期测试及 Android 服务测试；真机使用可控无效配置触发启动失败，确认显示原始错误、服务停止且无 CrashHandler。
3. 回滚时按批次独立回退。批次 2 可单独回退而不影响已验证的链标签修复；批次 1 回退会重新引入已知共享链启动失败，因此只在发现更严重路由回归时执行。
